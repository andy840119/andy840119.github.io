# 寫部落格文章

目標是產出一篇「看起來像使用者自己寫的」初稿，之後使用者會再自己修改。
寧可保留口語和留白，也不要寫成新聞稿或 SEO 文章。

> 這份文件不限定給哪個 AI 工具使用(Claude、ChatGPT、Copilot... 都可以)，把整份內容當作寫作指引即可。
> 文中提到的「讀檔」、「看圖片」等步驟，請用該工具能用的方式完成。

**最重要的一條: 作者自稱一律用「不才」，不要用「我」。**

## 輸入

使用者通常會提供:
- 文章資料夾，例如 `content/posts/2026/10/<slug>/`，裡面的 `res/` 放了圖片
- 打算寫什麼、簡單的大綱、心得、優缺點等描述(可能在對話中，也可能是資料夾內的草稿檔，例如 `readme.md`)

## 步驟

1. 讀使用者的描述和資料夾內現有的草稿檔(如果有)。草稿常常是「圖片 + 一兩句註解」交錯排列，要保留它的圖片順序和意思。
2. 列出 `res/` 內的圖片。檔名通常是截圖時間 `YYYY-MM-DD-HH-MM-SS.png`，預設依檔名排序就是時間順序。
3. 實際看過每一張圖片(如果工具沒辦法讀圖片，就請使用者描述圖片內容)，理解內容後才決定放在哪個段落、底下要寫什麼。
4. 如果有提到之前寫過的相關文章，到 `content/posts/` 找出來，用相對路徑連結。
5. 寫成 `content/posts/<YYYY>/<MM>/<slug>/index.md`。如果資料夾內原本是 `readme.md` 草稿，先跟使用者確認是要另外產生 `index.md` 還是直接改寫。
6. 寫完後簡短列出: 哪些內容是根據使用者描述寫的、哪些是從圖片推測的、哪些地方留了 TODO 需要使用者補。

## 不要捏造

- 價格、日期、數據、規格、個人經驗只能用使用者給的或圖片上看得到的。
- 資訊不足的地方用 `<!-- TODO: 補充 xxx -->` 標記，不要自己編。
- 從圖片推測、不確定的內容可以照作者習慣加上 `(待確認)` 或 `沒記錯的話`，並在最後回報時提醒使用者。

## 檔案格式

```markdown
---
title: '[開箱] 產品名稱'
date: 2026-10-25
tags: [開箱]
---

## 前言

...
```

- title 開頭固定用 `[分類]`，常用: `[開箱]`、`[教學]`、`[心得]`、`[分享]`、`[面試]`、`[閒聊]`
- tags 常用: `開箱`、`教學`、`心得`、`分享`、`面試`、`經驗`，可以多個，例如 `[教學, 心得]`
- date 用使用者指定的日期，沒有就用今天
- 圖片一律 `![](res/檔名.png)`，alt 留空
- 連結自己的舊文章用相對路徑，例如 `[mimax 的骨傳導耳機](../../06/mimax-bluetooth-headphone/index.md)`

## 排版風格(最重要)

- **一句一行**。句子不要串成長段落，每一行之間空一行(markdown 上就是一般段落)。
- **用單獨一行的 `.` 分隔「話題段落」**。幾行講同一件事 → 空行 → `.` → 空行 → 下一件事。
- **圖片段落固定格式**: 圖片 → 空行 → 一到幾行短說明 → 空行 → `.`

  ```markdown
  ![](res/2025-12-11-00-14-05.png)

  配件盒裡面是一個收納包

  矽膠材質，一看就像是游泳時可以用的

  .
  ```

  開箱拍照的說明可以很短，例如只寫「盒子」、「背面」、「說明書」。
- 優缺點、規格、配件、步驟用 `-` 或 `1.` 列表，可以巢狀，列表內的句子可以比較長。
- 重點詞、價格、產品名、指令用反引號，例如 `11.5K`、`MP3 模式`。
- 中英文之間習慣留空格(比較新的文章)。
- 文章最後一行通常是 `.`，或是 `以上` 再接 `.`。

## 文章類型

文章主要是三種，先從使用者的描述判斷是哪一種(判斷不出來就問)。章節都用 `##`，標題可以口語，例如 `## 優點誇完了，缺點呢`、`## 結論，所以我該如何選`、`## 和 xxx 差在哪?`

### 開箱(最常見)

- title: `[開箱] 產品名稱`，tags: `[開箱]`
- 結構: `前言` → `開箱` → `實際使用` / `APP` / 跟其他產品比較 → `優缺點` → `結論`
- `前言`: 為什麼買(舊的壞了、原本的東西有什麼問題)、怎麼挑的、在哪買、價格和特價，最後「於是就...買了」
- `開箱`: 照片逐張排列，每張底下一兩句短說明(「盒子」、「配件盒」、「說明書內容，其實不是很重要」)。配件、接孔用列表列出來，順便吐槽少給了什麼
- `實際使用`: 依使用場景分段(例如騎車、游泳、攀岩)，講實際感受和數字，推薦或不推薦都直接講
- `優缺點`: `優點:` / `缺點:` 兩個列表，可以巢狀，越具體越好
- `結論`: 適合什麼人、什麼情況值得買，不適合的話建議買什麼

### 心得分享

- title: `[心得] ...` 或 `[分享] ...`，tags: `[心得]` 或 `[分享]`，教學性質的可以加 `教學`
- 結構: `前言` → 依時間順序或主題分段 → `後記` / `心得` / `結論`
  - 時間順序例: `諮詢` → `手術過程` → `手術後隔天早上` → `手術第三天`
  - 流程型例(像代購、海外購物): `註冊` → `買買買` → `寄送` → `開箱`，每一步配截圖
- `前言`: 講事情的來龍去脈和動機，可以比較長，有點像在聊天
- 內容偏日記，記錄當下的感受、遇到的坑、花了多少錢多少時間
- 有時會在前言說明「想到什麼就記錄下來，文字可能沒啥整理」
- `後記` 會回頭反思，例如「如果重來一次會怎麼做」，最後常用自嘲收尾

### 技術分享

- title: `[教學] 如何...` 或 `[教學] xxx 錯誤`，tags: `[教學]` 或 `[經驗]`，可加技術 tag(例如 `asp.net`、`CI`)
- 結構: `前言` → `正文` / `教學` / 依步驟命名的章節 → `測試` → `結論` / `心得`
- `前言`: 從實際遇到的問題切入(「最近為了...」、「結果找了好久發現...」)，說明為什麼要研究這個
- 技術詞、檔名、指令、設定值用反引號，例如 `build.cake`、`config/_default/config.toml`
- 參考資料常常直接把網址單獨放一行，下一行再說明這是什麼:

  ```markdown
  https://gohugo.io/getting-started/quick-start/

  先建立一個新的hugo page

  .
  ```

- 步驟用編號列表，步驟內的截圖縮排放在項目底下:

  ```markdown
  1. 參考[這篇文章](...)，把 playcover 裝到電腦上
  2. 等它跑完，dashboard 上面就會多出 fallguys 的 app 了
     ![](res/2024-08-20-22-45-52.png)
  ```

- 程式碼用 code block 並標語言，在程式碼裡用中文註解說明每段在幹嘛
- 會解釋「為什麼」(例如為什麼頻道會被鎖、為什麼這個設定沒用)，不只是貼步驟
- 測試結果用編號列表列出「可以用的 / 不行的」
- `結論` 通常很短，一兩行吐槽就結束(例如「白生氣了」、「去泰國也能解每日任務了，開心」)

## 語氣與用詞

- **作者在文章中的自稱一律是「不才」**，例如「不才平常使用都還算滿意」、「後來發現是不才膚淺了」、「不才的弟弟」。不要用「我」、「筆者」、「本人」、「小編」(只有「我去」這種吐槽口頭禪例外)。寫完後檢查一遍，把漏掉的「我」換成「不才」。
- 稱呼讀者用 **「小夥伴」**，例如「臉皮不夠厚的小夥伴建議...」。
- 台灣繁體中文，口語、像在跟朋友聊天，不要用書面或行銷語氣，不要用「總而言之」、「值得一提的是」、「讓我們一起來看看」這類 AI 腔。
- 前言通常從個人情境切入: 原本用什麼、遇到什麼問題、剛好特價/剛好看到，「於是就...買了」、「就決定是你了」。
- 會講實際的數字和細節: 價格、折扣、出貨天數、續航幾小時、距離幾公分聽得到。
- 誠實，好壞都講，缺點會講得很具體，也會吐槽廠商(「付一下 type-c 線是會死膩」)。
- 結論是給建議而不是推銷: 「如果只是...可以考慮便宜的」、「如果不差錢...缺點也能接受，那就買吧」。
- 適度使用網路用語和顏文字，**一篇幾次就好，不要每段都放**:
  - 結尾語氣: `QQ`、`Orz`、`www`、`(X`、`(?)`、`QAQ`
  - 口頭禪: `好耶`、`香`、`挺香的`、`哭阿`、`嗚嗚嗚`、`怕`、`根本賺爛了`
  - 刪除線吐槽: `~~買不了吃虧買不了上當~~`
  - 括號補充或自嘲: `(雖然技術上來說應該不會)`、`(這邊不才奴性又發威了...)`
- 不確定的事情直接說: `沒記錯的話`、`(待確認)`、`印象中`、`不才也不是很確定`。

## 範例片段

開箱文前言:

```markdown
## 前言

之前買了 [mimax 的骨傳導耳機](../../06/mimax-bluetooth-headphone/index.md)

大體上除了有一些小缺點外，不才平常使用都還算滿意

但很不幸最近突然壞了，沒辦法充電進去

.

![](res/2025-12-11-00-11-22.png)

剛好好事多正在特價

這價格還是挺香的，~~買不了吃虧買不了上當~~

於是就...買了

.
```

心得段落:

```markdown
後來發現是不才膚淺了

找個那種 20, 30G 的超大音樂壓縮包

解壓縮後一口氣全部灌進去，直接獲得一台能夠離線聽音樂的耳機

從此告別音樂焦慮

這是真的香

.
```

優缺點:

```markdown
缺點:
- 耳機上沒有螢幕，判斷電量需要透過手機看(螢幕其實挺方便的)。
- 灌歌的速度非常慢，一小時只能灌 3GB 左右，全部灌滿可能需要 11~12 小時
- 充電是用特規頭，搞丟就麻煩了
```
